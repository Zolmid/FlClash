# 操作边界、证据与开发交接

适用业务源码基线：`d0af9d83c4f37199caceb436b3c3ae66cdb36cd6`。本章面向维护者和执行开发任务的 Agent，说明如何把一次修改交付成可继续维护的结果。具体构建、发布和恢复命令见 [CI、发布与恢复](ci-release-and-recovery.md)，实际验收记录见 [验证基线](verification-baseline.md)。

## 1. 先判断任务属于哪一层

| 操作 | 默认处理 | 必须说明的条件 |
|---|---|---|
| 读取已授权仓库、日志元数据、CI、公共清单 | 使用已有连接只读核对 | 不输出凭据、完整环境或真实用户配置 |
| 隔离工作树内修改、生成、单测、文档、本地提交 | 按当前任务自主推进 | 有准确基线、唯一写入者、最小验收和恢复点 |
| 安装依赖或构建 | 先检查脚本及工具链副作用 | 不升级固定版本来掩盖失败，不默认启动 App |
| 普通功能的内部重构 | 保持用户行为和数据兼容 | 先有特征测试，状态权威不复制到另一层 |
| 功能/平台退役、身份或 schema 变更 | 单独提出具体决定 | 列旧入口、旧数据、共享能力、各平台和回退 |
| main/远端 refs、CI 编排、正式 tag、签名/公证/发布 | 依当前准确授权执行 | 目标 SHA、动作、受影响入口、验证与回退必须明确 |
| 真实设备、代理/DNS/TUN、特权服务、用户数据 | 先选定隔离资源和测试窗口 | 捕获原状态，限定自有资源，只恢复本次改动 |

普通工程命名、内部接口和测试组织不需要逐项问用户。真正的授权缺口只阻塞依赖它的任务，不停止其他已获准工作。已经完成的一次发布或 A1 主线切换，不会自动授权下一次正式版本或不同 SHA。

## 2. 多仓库工作区不能当作一个 monorepo

整包中客户端、面板、节点、发布 Edge、实时 Edge 和其他工具是独立工作区。客户端源码位于本仓库；后端源码在整包的兄弟目录中，例如：

| 连接区域 | 维护者需要对齐的内容 |
|---|---|
| `packages/zolnit_client` 与面板 Client API | 请求/响应、账号绑定、签名订阅、到期与撤销、设备语义 |
| `native_ui/contract.v1.json` 与原生展示插件 | 快照版本、字段、命令、可用性及错误反馈 |
| `tool/client_release` 与 `workspaces/xboard-ops/work/client-release-edge` | OIDC、版本不可变性、分片上传、清单、发布/通知结果 |
| 独立 Apple 工具与 Suite 的 `Modules/Client` | 工具 pin、source tag、归档/设备任务、调度器与回执 |
| 实时客户端与 `client-realtime-edge` | 协议版本、鉴权、重连、事件序号及 HTTP 回退 |

兄弟目录路径是整包布局提示，不是 GitHub 克隆后必然存在的文件。只取完成任务必需的源码或脱敏契约，不把受限部署目录复制进客户端仓库。不能在整包根目录初始化 Git、批量 add 或合并独立历史来“统一项目”。

## 3. 工作区与所有权

开工记录包括 repo、完整 HEAD、分支、工作树 dirty 状态、父级公共 Git 目录、子模块、当前运行实例以及输出目录。Git worktree 共享对象和 refs，不是独立安全沙箱；SDK 缓存、端口、模拟器和构建输出也可能共享。

一个可变目标只允许一个写入者。尤其注意公共模型、装配入口、provider 状态、Core/原生桥、schema、锁文件、生成配置、workflows 和发布脚本。涉及这些位置时先明确合同、负责人和下一交接点。

以下都是错误的接管方式：

- 别人尚未回复，就把其工作区 reset 到自己选择的基线。
- 将 wait 超时解释为执行者已经停止，然后另开一个 writer 写同一目录。
- 为得到干净状态，把原来的未跟踪文件加入自己的提交。
- 认为源码 worktree 独立，就可以并行占用同一个设备或构建目录。

发生冲突时保留现场，只暂停受影响路径。确认旧执行者已停止或交回后才能重分配；不要取消 APP Agent、共享服务或不属于本任务的 CI。

## 4. 一次变更的可验收闭环

1. **冻结输入。** 给出完整源码 SHA、适用契约版本及用户要求。工作树有自有未提交输入时记录 patch/content digest。
2. **证明旧行为。** 选择能区分正确/错误的现有测试或最小特征用例。先确认命令没有真实网络、签名、上传或数据副作用。
3. **做最小完整修改。** 保持既有数据格式、身份、状态所有者和正式流程，避免无关格式化和依赖升级。
4. **自测。** 保存真实命令、退出码、环境和被测输入；测试失败不能靠删断言、宽泛 skip 或降低门槛消失。
5. **独立审查。** 审查精确 BASE→HEAD 的实际 diff、调用方和测试。结论要有路径、触发条件和影响，不按模型投票。
6. **候选集成。** 在主控自己的干净集成分支串行合入，再运行相关组合回归。物理合入不自动表示验收完成。
7. **晋级验证基线。** 组合回归通过后更新 verified SHA；失败候选不能解锁依赖它的下一批代码。
8. **保存检查点和交接。** 记录尚未完成的动作及最小恢复步骤，结束或明确归属所有本次执行者。

文档修改的验收重点是事实、相对链接、命令和风险分类，不为凑流程跑五平台重型构建。代码变化后的检查按影响范围失效；未改变的部分可以复用既有证据，但必须说明“同一内容”如何确认。

## 5. 证据应回答什么

每份结果至少回答：

- 测的是哪个 repo、完整 SHA、实际工作树和输入摘要？
- 使用了哪些实际工具版本、平台/架构和构建参数？
- 哪个命令或测试确实执行，退出码与实际结论是什么？
- 哪些内容来自直接观察，哪些只来自别人报告、推断或尚未知？
- 检查能证明哪一层，不能证明什么？
- 输出、日志或回执在哪里，是否含秘密，如何重现？

使用 `OBSERVED / REPORTED / INFERRED / UNKNOWN` 区分事实来源；用户许可另记 `USER_AUTHORIZED`。结果使用 `PASS / FAIL_NEW / FAIL_BASELINE / BLOCKED_ENV / NOT_RUN / NOT_APPLICABLE`，最后一种必须有适用范围理由。

例如：32项选择器/发布辅助测试实际在 GitHub Dart job 中通过，是托管 V1 证据；iOS unsigned/ad-hoc 构建完成是 V2；两者都不能替代手机安装、VPN 生命周期或发行证书验收。

## 6. 数据和日志处理

登录凭据、订阅令牌、支付 client secret、原始敏感深链、节点 UUID、签名材料和真实用户配置不得进入聊天、提交、工单或公开文档。排障报告优先保留错误码、阶段、时间、版本、来源摘要和脱敏结构。

真实凭据由既有受限存储和授权连接使用，不复制全局 OAuth、浏览器 cookie 或系统钥匙串。新设备由本人重新登录。命令行参数、shell history、进程列表和 CI 日志同样可能暴露信息；不要用“只是一条测试命令”作为泄漏理由。

公开报告不需要真实设备标识。设备资源标识保存在受限验收记录中；公开部分写设备类别、系统版本、测试范围与结论即可。

## 7. 恢复时不要重放副作用

恢复流程先读状态与执行实例，再核对实际 Git、工作树、进程/worker 和 CI。不能把保存的 `RUNNING` 改成成功，也不能假设缺失消息代表旧 writer 已消失。

| 停止点 | 恢复动作 |
|---|---|
| 只完成源码修改 | 读实际 diff，确认归属，继续缺失检查 |
| 独立审查通过但未集成 | 核对输入/契约未变，再串行集成和组合回归 |
| 候选已合入但验证失败 | 保留上一验证基线；修复或撤销自有提交，不用候选HEAD解锁下游 |
| CI已派发，未收到终态 | 用保存的run ID/attempt查询，不盲目再dispatch |
| 已签名或公证pending | 使用精确回执/checkpoint和原字节，不重新签另一份 |
| Edge成功、镜像失败 | 只恢复未完成副作用，先核对同版本内容一致 |
| 旧执行者停止状态未知 | 保留所有权与未结清预留，不派重叠writer |

代码回退和数据回退是两件事。Git revert 不能撤销已写入用户数据库的迁移、系统代理/DNS变化或已发布资产。正式版本不得同版本覆盖；可能必须创建新的版本。

## 8. 发布或重大切换的批准包

批准对象应是可审阅的准确结果，而不是“允许我优化一下”。至少包括：repo/ref/完整SHA、旧值→新值、每个实际写动作、消费者、必需检查、执行顺序、停止条件和回退方式。

外部信任切换需要覆盖所有已知入口和在途任务。一次队列为空不是迁移栅栏；要么阻止相关新任务进入，要么证明每个任务全程使用一条完整的固定旧链或新链。出现混合 pin/OIDC/environment、未知入口或恢复权限不足时不开始切换。

普通只读和已授权的可逆工程工作不需要重复批准。批准只覆盖其准确范围和有效前提；候选构建许可不等于正式发布许可，模型建议也不授予权限。

## 9. APP Agent 与团队交接

已有 APP 会话持有产品语义、设备和未提交工作背景，但它的回复也要区分事实和历史。固定同步点是启动、共享接口、产品退役、阶段集成和主线/生产切换；普通内部命名不逐文件打断对方。

交接应包含准确 BASE/HEAD、变更路径、状态/数据/身份契约、真实验证、未验证项、WIP/资源归属、仍在运行的执行实例及下一动作。消息状态使用 `DRAFT / SENT / RECEIVED / ACKNOWLEDGED / CHANGES_REQUESTED / BLOCKED`；写好文件不等于已发出，没有回复不等于同意。

本轮 A1 已得到 APP 的明确 ACK：后续获准开发以 `main@d0af9d83` 为基线，使用隔离工作树，公开版本仍为1.1.9。原617154da工作树及其未跟踪内容保留。新的维护任务仍需重新核对当前refs，而不是永久锁死在本文的日期快照。

## 10. 更新本手册

新功能应同时更新功能清单、负责层、非UI入口、数据/平台影响和相应测试。变更发布流程时更新生产者/消费者、来源字段、实际检查、恢复和授权边界。把可断言行为写入测试，把跨文件规则写入适用仓库文档；不要仅在某一处注释里藏维护契约。

本地控制记录属于整包运维资料，通常位于 `.dev/flclash-refactor-20261115/control/`，不随独立客户端克隆保证存在。可移植的源码说明与公共CI链接保留在本手册；秘密和机器专属恢复材料留在受限存储中。
