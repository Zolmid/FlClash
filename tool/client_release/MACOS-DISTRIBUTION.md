# macOS direct distribution

When enabled, the formal tag workflow requires Developer ID signing and Apple notarization for both macOS architectures. It reuses the app archives built by the same workflow run; it does not rebuild the app or use Mac App Store distribution. Existing Cloud Build manual runs remain unsigned preparation builds.

Before requiring macOS signing for a formal release, configure repository variables `MACOS_SIGNING_REQUIRED=true` and `MACOS_TEAM_ID` (the ten-character Team ID). Configure the protected `macos-distribution` environment and its reviewers, then add these **environment secrets**:

- `MACOS_DEVELOPER_ID_P12_BASE64`: base64 of a password-protected P12 containing the Developer ID Application leaf certificate, its private key, and the public Apple Developer ID intermediate CA certificate that issued that leaf.
- `MACOS_DEVELOPER_ID_P12_PASSWORD`: password for that P12.
- `APPLE_ASC_API_KEY_ID`, `APPLE_ASC_ISSUER_ID`, `APPLE_ASC_P8_BASE64`: App Store Connect team API key ID, issuer ID, and base64-encoded P8. The owner must verify that the key has permission to use the notary service.

Both workflow callers explicitly forward these five names, and the reusable workflow declares them required. The values remain environment-scoped: each concrete job binds `macos-distribution`, and Linux wait jobs receive only the three API secrets. The entry preflight reports presence booleans, never values, and rejects blank secrets before source-artifact download.

The owner must supply the intermediate matching the leaf certificate issuer; for a newly issued certificate this is normally Apple Developer ID Certification Authority G2. Obtain and verify the public intermediate from [Apple](https://developer.apple.com/support/developer-id-intermediate-certificate/) during the later approved credential setup. The runner must have the corresponding Apple root trusted by its system trust store; importing an intermediate does not establish trust in an untrusted root. The P12 import installs the supplied certificates in the temporary keychain. A leaf and private key alone may not produce a valid identity on a clean runner, and missing or untrusted chain material fails the job. Do not add trust overrides.

The signing job creates a temporary keychain and restricts its search to that keychain plus the existing user search list. It selects exactly one valid `Developer ID Application: … (TEAM_ID)` identity for the configured team; Apple Distribution, Mac App Distribution and Developer ID Installer identities are rejected. It signs embedded Mach-O files and bundles inside out with hardened runtime and secure timestamps, then signs the app with the existing release entitlements. It submits a zip of the app without waiting on the Mac runner. A Linux job polls the Notary API, then a Mac job staples and validates the app and assesses it with Gatekeeper before building and submitting the DMG. A second Linux wait and Mac finalization verify the DMG before any final artifact is emitted. Temporary credentials and the keychain are removed and the search list restored. Passwords are sent to the interactive `security` process on stdin; they are not command arguments.

Each signed artifact contains the final DMG and a receipt tying its SHA-256 to the same-run source app archive, source commit, team and notarization submissions. The formal assembler requires both signing jobs and checks the receipt, source archive digest, artifact digest and final DMG digest before creating its manifest. With the repository variable unset or set to `false`, the signing jobs are skipped and the existing release path remains available; its macOS DMGs are not notarized. When it is `true`, a skipped or failed signing job blocks publication. The preflight captures the setting once for both jobs and rejects other values.

These checks do not replace owner approval or a real signed build and device acceptance. CI needs access to Apple's timestamp, notary and ticket services; a credential, trust-chain, API authorization, rejection, timeout or Gatekeeper failure fails the job. Do not enable the variable until the owner approves the environment and credentials.

macOS currently launches `FlClashCore` directly and has no hash-bound privileged Helper or Core manifest. Signing changes Core bytes; do not copy the Windows/Linux Helper manifest scheme onto macOS. The signing tool rejects an unexpected runtime Core manifest or privileged Helper so an embedded Core hash cannot silently become stale if the bundle architecture changes.

For a non-publishing verification, an owner may enable the repository variable `MACOS_NOTARIZATION_VERIFY_ENABLED=true` and manually dispatch `macos-notarization-verify.yml` on `codex/native-client-shared` with a successful formal release run ID and its tag. The defaults select run `42474933687` and `v1.1.4`. The protected `macos-distribution` environment still applies. A push only registers the workflow and skips the verification job; no publication is performed. The workflow checks the source run and tag via GitHub, verifies same-run artifact digests and provenance, retrieves the source commit's version and entitlements, then signs both architectures. Successful DMGs and receipts are retained as workflow artifacts for seven days. This does not replace the public release or enable the formal signing gate.

Before signing a bundle supporting macOS 12, the tool materializes the legacy login item if absent from the checksum-pinned upstream `LaunchAtLoginHelper.zip`, validates the archive, and sets its bundle ID to the main ID plus `-LaunchAtLoginHelper`. Existing valid login items are retained. The helper is signed before the app with hardened runtime, a secure timestamp, its required entitlements and `get-task-allow=false`. The tool then removes only `LaunchAtLoginHelper.zip` and `LaunchAtLoginHelper-with-runtime.zip` from the SwiftPM resource bundle. These are build-time templates; macOS 13+ continues to use `SMAppService.mainApp`. Actual login-item behavior requires device validation.

## Pending submissions and retries

Manual and formal signing share `macos-notarization-pipeline.yml`: Mac app submission → Linux app acceptance → Mac app stapling and DMG submission → Linux DMG acceptance → Mac finalization. Linux uses Node 22's built-in crypto and fetch APIs; only the App Store Connect key is provided there, never the Developer ID P12. Each Linux wait is bounded to five hours with one read-only status request per minute. Mac stages do not wait for Apple processing. The existing environment approvals apply to each stage.

Before upload the signer saves the exact signed payload and its digest, then persists the returned submission ID before any wait. Each checkpoint contains only `pending-receipt.json`, `notary-app.zip`, and, once created, `notary-dmg.dmg`. Workflow uploads list these files explicitly, including on failure, with seven-day retention. P12, P8, keychain, passwords, raw command output, and scratch files are never checkpoint members. An upload error with no returned ID is recorded as an unknown outcome and requires operator reconciliation; it is never automatically resubmitted.

Checkpoints bind source repository, commit, run, version, architecture, fixed Core revision, original artifact ID and digest, source provenance digest, original app archive digest, team, signing identity and submission IDs. Resume checks the checkpoint producer workflow/run and outer artifact digest, the source run/tag and source-file metadata, the saved payload hashes, and the Developer ID team/signatures, timestamps and hardened runtime. It does not redownload the original source app ZIP, so original build-artifact expiry does not prevent continuation. A DMG resume additionally checks its mounted app and stapled app ticket without launching the app. The same signing identity must remain valid and available.

For a fresh manual verification, `start_new=true` is now an explicit opt-in, after checking previous submissions. To resume in a new dispatch, leave it false and supply `resume_arm64_artifact_id` and `resume_x64_artifact_id` from the trusted checkpoint artifacts. Each architecture is validated separately; no arbitrary submission ID is accepted. GitHub failed-job retries use the newest prior checkpoint for that architecture. A retry with no checkpoint fails closed rather than creating a duplicate. Already-successful stages need not be rerun. A DMG-stage retry prefers an existing same-run DMG/final checkpoint over the upstream app checkpoint. Without one, read-only prior-attempt job history must establish that the DMG signing step never executed; otherwise the retry stops for reconciliation. A global retry caused only by the app-status wait can therefore proceed to its first DMG submission.

Acceptance within a Linux wait automatically releases the next Mac stage and, for a formal run, the final assembler/publish gate after both architectures succeed. A pending timeout, rejection, signature failure or missing evidence cannot produce release success. After the wait bound, an authorized failed-job retry resumes the saved ID; no manual file re-upload is needed. If the checkpoint itself expires, recovery requires a retained verified copy and review. The earlier timed-out jobs that did not retain their exact signed inputs are not recoverable through this checkpoint path. Do not treat a later Apple acceptance of those lost inputs as validation of newly signed bytes.
